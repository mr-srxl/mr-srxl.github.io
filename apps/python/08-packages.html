08 · Modules & packages

Python's real strength is the ecosystem. This chapter is about using other people's code — and about shipping your own cleanly.

Importing modules

# Whole module
import math
print(math.sqrt(16))       # 4.0

# Specific things from a module
from math import sqrt, pi
print(sqrt(16), pi)

# Give it a shorter name
import datetime as dt
print(dt.date.today())

Writing your own module

A module is just a .py file. Create helpers.py next to your script:

# helpers.py
def double(x):
    return x * 2

def shout(text):
    return text.upper() + "!"

Then import from it in another file:

# main.py
from helpers import double, shout

print(double(5))         # 10
print(shout("hello"))    # HELLO!

Installing packages — pip

The standard library is huge, but the third-party world is enormous. Packages live on PyPI (pypi.org) and you install them with pip, which comes with Python.

# Install a package
pip install requests

# Install a specific version
pip install requests==2.31.0

# Upgrade
pip install --upgrade requests

# List what's installed
pip list

# Uninstall
pip uninstall requests

Virtual environments — one per project

Different projects want different versions of the same package. A virtual environment gives each project its own isolated set of packages. Use one per project, always.

# Create a virtual environment inside the project folder
python -m venv .venv

# Activate it
# Windows (PowerShell):
.venv\Scripts\Activate.ps1
# Windows (cmd):
.venv\Scripts\activate.bat
# macOS / Linux:
source .venv/bin/activate

# Now pip installs go into .venv, not your system Python
pip install requests

# Leave when you're done
deactivate
Heads up: add .venv/ to your .gitignore. Never commit the virtual environment folder — it's huge and machine-specific.

requirements.txt — what it is and why it matters

A requirements.txt is a plain text file listing every package your project needs, with the exact versions you tested with. Anyone (including future-you on a new laptop) can recreate the exact environment with one command.

Creating one

# After activating your venv and installing what you need:
pip freeze > requirements.txt

What it looks like

requests==2.31.0
rich==13.7.0
python-dotenv==1.0.1

Using someone else's requirements

# On a fresh machine:
git clone https://github.com/someone/project.git
cd project
python -m venv .venv
source .venv/bin/activate    # or Windows equivalent
pip install -r requirements.txt

That's it — you now have the exact same packages the author used.

Try this: make a new folder, create a virtual environment, activate it, install the rich package, then run pip freeze > requirements.txt. Open the file — you should see rich listed with its version.
